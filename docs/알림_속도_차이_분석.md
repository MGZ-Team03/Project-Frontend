# 알림 속도 차이 분석

## 1. 학생 알림 (빠름 ⚡) - 동기 처리
```
튜터 승인/거부 → Lambda → [동시] WebSocket + DynamoDB 직접 저장
```
- 지연 시간: **< 1초**

## 2. 튜터 알림 (느림 🐢) - 비동기 처리
```
학생 등록 요청 → Lambda → WebSocket (즉시) + SQS (비동기)
                                          ↓
                              Lambda Consumer → DynamoDB (1~5초)
                                          ↓
                              프론트엔드 폴링 → 뱃지/목록 업데이트
```
- 지연 시간: **1~10초**

## 3. 비교 요약

| 구분 | 학생 (승인/거부) | 튜터 (등록 요청) |
|------|-----------------|-----------------|
| DB 저장 | 동기 (직접) | **SQS 비동기** |
| 토스트 | 즉시 | 즉시 |
| 뱃지/목록 | 즉시 | **폴링 대기** |

## 4. 프론트엔드 대응 (`useTutorNotifications.js`)
1. **토스트**: WebSocket 수신 즉시 표시
2. **뱃지/목록**: 1초 간격 폴링 (최대 10회)

## 5. 백엔드 해결 방안

| 옵션 | 방법 | 장단점 |
|------|------|--------|
| A | SQS 제거, 직접 저장 | 빠름 / 재시도 로직 필요 |
| B | DB 저장 후 WebSocket | 일관성 / 토스트도 지연 |
| C | DynamoDB Streams | 정확함 / 인프라 추가 |

## 6. 결론
- **원인**: SQS 비동기 처리로 DB 저장 지연
- **현재 대응**: 토스트는 즉시, 뱃지는 폴링
- **권장**: 현재 구조 유지
